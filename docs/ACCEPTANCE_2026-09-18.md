## 本轮发现的代码缺陷

P1 表示应在真实用户上线前处理；P2 表示确定存在、应在下一修复批次处理。下列触发条件都是必要边界，不表示问题在每个请求中发生。

### F1 / P1：退出失败被伪装为成功

- 位置：`dk-ai-agent/dk-ai-agent-frontend/src/stores/auth.js:83–89`；相关 API 拦截在 `src/api/index.js`。
- 触发：`POST /auth/logout` 因 CSRF token 过期返回 403，或因网络失败没有到达服务端。多标签页中另一页登录并轮换 token 是过期 token 的一个来源。
- 行为：store 吞掉全部异常，清空本地身份，调用方继续跳转登录页。403 被 CSRF 过滤器拒绝时，控制器的 `session.invalidate()` 不会执行；刷新后仍可能恢复服务端身份。
- 影响：用户以为已退出，实际凭据仍有效，共用设备上尤其不合适。
- 证据：前端探针让真实 store 的 API 调用拒绝为 `CSRF_INVALID/403`，`logout()` 仍成功返回且本地身份被清空。服务端不失效的结论来自过滤链与控制器路径复查；未伪称此探针运行了真实服务器。
- 修改与验收：对 CSRF 失败刷新 token 后仅重试一次退出；对网络错误明确显示“尚未确认退出”，不能吞掉。覆盖 204、已失效 401、403、网络中断、多标签页；成功退出后 `/auth/me` 必须未认证。

### F2 / P1：历史风险没有进入输出拦截的判定

- 位置：`CounselingTurnPipeline.java:96,118`；对照 `SafetyDirectives.java:83–87`。
- 触发：前轮表达风险，当前只回复“嗯”等无显式关键词的短句。
- 行为：历史消息会产生“持续关注”提示词，但管线只用 `SafetyTerms.assess(request.message())` 决定是否启用 `SafetyOutputGuard`，当前句被判 NONE 后原样放行模型文本。
- 证据：同一“尊重你的决定”模拟模型输出，在当前输入有风险时被替换，在上述短回复时直接通过；历史消息同时确实能触发持续关注指令。
- 影响：刚进入高风险情境，硬性输出检查可能下一轮就撤下，风险连续性主要依赖模型遵循提示词。
- 修改与验收：在会话范围维护有明确解除/过期策略的风险状态，提示词与输出检查共用判定。历史风险不应永久强制危机模板，但在确认解除前应保留适当输出检查。补多轮用例、模式切换、重试与服务重启场景；具体风险策略还需独立人工评审。

### F3 / P2：一次登录失败释放了所有在途名额

- 位置：`account/LoginAttemptService.java:69–83`。
- 触发：5 次密码比对已获准且未全部结束，其中一次先失败，随后到达新请求。
- 行为：`recordFailure()` 将 `inFlight` 直接设为 0，而非归还当前请求的一个名额。
- 证据：先准入 5 次 → 记录 1 次失败 → 另外 4 次仍获准；同一窗口已准入 **9 次**，与代码注释“严格 ≤ 5”的承诺冲突。既有并发测试只测同时准入，漏了准入与结算交错。
- 修改与验收：只扣除本次名额，并处理窗口切换/成功清零时的旧请求结算归属；用确定性交错测试验证 `failures + inFlight` 预算不会被提前释放。

### F4 / P2：密码重置和登录交错，旧凭据仍可建立新会话

- 位置：`controller/AuthController.java:102–114,149–156`；`account/UserAccountService.java:144–146`。
- 触发顺序：旧密码校验已成功 → 管理员重置密码并完成会话吊销 → 原登录请求继续登记会话。
- 行为：登记后只复查账号是否 ACTIVE，没有复查凭据版本；重置密码没有改变 ACTIVE，故新会话存活。
- 证据：探针使用实际 BCrypt、账号服务、控制器和会话登记服务，只替换存储并固定上述调度顺序。旧密码已不匹配新哈希，控制器仍返回 200 并保存认证上下文。
- 影响：密码轮换的吊销边界存在时间窗口；不是“任何旧密码都能在重置后登录”，也不等于匿名可利用。
- 修改与验收：引入凭据版本或等价的版本复核，登记后同时校验状态和认证所用版本；改密/重置要使旧版本失效。覆盖重置前后各个交错点及自己的改密流程。

### F5 / P2：文本内容与完成信号共用 `[DONE]`

- 位置：`agent/counseling/CounselingTurnPipeline.java:199–203`，以及准备后的标准模型流。
- 触发：模型某个内容分片恰好等于字面量 `[DONE]`。
- 行为：被映射为完成事件，后续真实文本被取消，已输出的前缀却按 COMPLETED 保存。
- 证据：受控上游依次输出“前缀”、`[DONE]`、“后缀”、最终完成标记；结果只保留前缀并返回 done。
- 修改与验收：内部使用带类型的 delta/done 事件，或只由流正常结束产生完成事件；正文不得承担控制信号。覆盖标记出现在首段、中段及不同分片边界。

### F6 / P2：过期 `/auth/me` 响应能覆盖退出后的身份

- 位置：`dk-ai-agent/dk-ai-agent-frontend/src/stores/auth.js:31–48,65–68`。
- 触发：`ensureMe()` 请求未返回时调用 `clearAuth()` 或完成另一账号登录，随后旧请求返回。
- 行为：清除 `inflightMe` 引用没有作废原 Promise，其 `then` 仍能写入旧身份。
- 证据：启动受控 `/me` Promise → 清空身份 → 返回旧用户；`isLoggedIn` 又变为 true。
- 影响：界面身份和路由可能回滚；服务端仍独立鉴权，未据此认定跨账号越权。
- 修改与验收：给认证状态引入版本号/请求世代，状态切换时作废旧结果，必要时取消请求；覆盖退出、重新登录和并发 force 刷新。

## 发布及业务质量的验收缺口

### R1：提交版发布包缺少 Docker 必需文件

`frontend/Dockerfile:12` 需要 `security-headers.conf`，但 `98b3c5f` 对应打包脚本的前端白名单没有该文件。当前工作区已增加这一行，说明问题有修正，但还未进入 Git 提交。

本次静态交叉核对已确认依赖缺失；没有在 Docker 不可用时虚构容器构建失败日志。应提交现有修正，并从干净检出生成发布包、再从解压包构建镜像，把打包后的构建检查纳入 CI。仅在完整仓库根目录构建不能覆盖这一缺陷。

### R2：检索有基线，尚无质量合格证据

本轮独立复跑仍为 25 个来源案例查询中命中 1 个，MRR@4 0.02；5 个无关输入全部产生结果。评测用实际 Markdown 加载器和当前 Transformers 嵌入模型，精确余弦 topK=4、阈值 0.3。

这些标签是按来源案例建立的种子标签，未穷尽其他语义相关案例，也未经过独立人工审核，**不能把 4% 解释为真实问答准确率**。评测不覆盖 pgvector 近似索引、深度规划/重排或最终回答。测试只断言评测运行完成，没有质量门槛；“基线测试通过”与“检索合格”是两件事。

下一步应先独立标注相关性并保留验收集，比较中文/多语种模型、分块、混合检索和阈值，确定质量与延迟门槛后再验收。不能只反复优化这 30 条种子然后宣布有效。

### R3：敏感数据保护和上线运行证据不足

数据库正文、摘要及短期回放答案没有应用层加密。磁盘和备份是否加密、密钥及访问权限配置、删除/恢复演练不在本轮可确认范围内；不能从“列中明文”直接推断所有存储介质均无加密，也不能因此宣布敏感数据保护通过。

系统明确只支持单副本、停旧再起新：启动恢复全部 RUNNING，认证会话、限流和部分内存状态也是进程内。多副本/重叠滚动部署不是现有支持能力。生产前还需真实 TLS Cookie/CSRF/SSE 验收、备份恢复、故障场景、负载与长会话验证。现有 180 秒上限和局部并发隔离不能替代容量测试。

### R4：测试与可观测性仍有空白

CI 配置已存在且 Maven wrapper 执行位已修正；本轮没有远端运行证据。Java/Python 有行为测试，但不覆盖真实模型的输出安全和质量；前端没有完整浏览器 E2E。MDC 仅入口线程自动绑定，Worker 与其他模型调用的成本、错误率和异步关联尚未形成完整运维视图。Python 依赖仍为范围约束，跨时间重建的一致性也应补锁定与审计。
